# kakin-checker-app
ソシャゲのガチャ課金を手軽に記録・管理するWebアプリケーション
## 1. サービス概要

- <b>サービス名（仮):</b>ガチャ課金チェッカー
- <b>概要</b>:
  <p>
  ソシャゲのガチャ課金を手軽に記録・管理するアプリです。<br />3タップで記録でき、合計額は見たいときだけ確認できます。<br />罪悪感や入力の負担を減らし、無理なく課金ペースを把握できます。
  </p>
- <b>解決する課題</b>:
  - <b>対象</b>: ソシャゲのガチャに熱中して計画以上に課金してしまい、翌月の請求で後悔しがちな20〜30代のユーザー
  - <b>課題</b>: 課金をコントロールしたいが、従来の管理アプリは入力が面倒な上、アプリを開くたびに支出総額を突きつけられて現実逃避（ダチョウ効果）してしまい継続できない。
  - <b>解決策</b>: 事前登録タイトルから3タップ（約10秒）で完了する最小限の入力導線、合計額を意図した時だけ確認できる開閉設計、および「課金力」への単位緩和によって心理的ハードルを下げ、無理なく習慣化できる仕組みを提供します。

---

## 2. アイデアの背景

### 2-1. きっかけとなった体験・感情

- ソーシャルゲームで欲しいキャラクターをガチャで手に入れる瞬間は、日々の大きな楽しみでありストレス解消でもあります。
- 一方で、目当てのキャラが出ない興奮状態のまま勢いで課金を重ね、翌月の請求額を見て「想定以上に使ってしまった……」と強い罪悪感と後悔に苛まれる経験を何度もしました。
- その結果、せっかくキャラクターを入手できても、喜びより「いくら使ってしまったのか」という不安が勝ってしまい、ゲームを素直に楽しめなくなるジレンマに直面しました。

### 2-2. なぜそれが気になったのか

- 「来月は控えよう」と決意しても、ゲームに熱中すると同じ失敗を繰り返してしまい、根本的なペース管理ができていないことに気づきました。
- 課金を完全にゼロにして我慢したいわけではなく、「自分にとって安全な許容範囲を把握した上で、不安なく気持ちよくガチャを楽しみたい」という強い想いがあったためです。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

- 課金を管理したいと思っても、記録が億劫で三日坊主になり続かない。
- 家計簿アプリや決済明細では、日用品やサブスク等の他支出と混ざってしまい、純粋なソシャゲ課金額が把握しづらい。

### 3-2. 深掘りした真の課題（Whyの深掘り）

1. <b>なぜ管理が続かないのか？</b>
   - ガチャを回している興奮状態で、日付・タイトル・金額を細かく手入力するのが面倒だから。
   - 記録しようとするたびに「これまでの課金合計額」が目に飛び込んできて、楽しい気分が一気に冷めるから。
2. <b>なぜ金額を見ると気分が冷めるのか？</b>
   - 従来の管理アプリは「いくら使ったか」を直視させる設計のため、罪悪感からアプリを開くこと自体を避けてしまう（ダチョウ効果／ダチョウ症候群）。
3. <b>本当に解決したい課題</b>
   - 「現実を直視する苦痛や入力の手間を排除し、自分の課金ペースを把握して、罪悪感なく安心してガチャを楽しめる状態を作ること」

## 4. 想定ユーザー

### 4-1. ターゲット像

- <b>年齢層</b>: 20〜30代（独身・社会人）
  - <i>選定根拠</i>: スマホゲームへの課金比率・可処分所得が最も高い年齢層であるため。
- <b>生活・状況</b>:
  - 可処分所得にある程度余裕があり、余暇はソシャゲやSNS（X等）に時間を費やす。
  - 期間限定ガチャや推しキャラが登場すると「出るまで引く」傾向があり、月末・翌月のクレカ請求を見て青ざめた経験がある。
- <b>利用環境と課題へのアプローチ</b>:
  - 課金を行う瞬間はゲームに熱中した興奮状態であり、すぐにゲームに戻りたいため、細かい入力フォームを埋めることは極めて困難。
  - <b>アプローチ</b>: 事前登録したタイトルから金額ボタンを選ぶだけの「3タップ／約10秒」で完了するUIを設計し、熱中状態を邪魔せず記録できる環境を実現します。

### 4-2. ユーザーとの距離感

- <b>当事者（自分自身）</b>
  - 自身の現在も続いているリアルな課金体験・後悔・管理挫折の経験から着想を得ており、ユーザーの細かな心理的機微（見たくない・でも把握したい）を当事者目線で正確に捉えています。

### 4-3. 需要と代替手段の比較

- <b>想定初期ユーザー</b>: SNS等で「課金しすぎてクレカが止まった」「今月の請求が怖い」と投稿しているソシャゲユーザー。
- <b>代替手段（現状）</b>: クレジットカード・決済アプリの利用明細、一般的な家計簿アプリ、メモ帳。
- <b>代替手段からの移行理由</b>:
  - クレカ明細は生活費等も含まれ、ソシャゲ単体の支出が直感的に見えにくい。
  - 家計簿アプリは「節約・我慢」を目的としており、課金を楽しむマインドと相反する。
  - 本アプリは「課金を否定せず、安心して楽しむための相棒」として機能するため、置き換えて利用する明確な価値があります。

### 4-4. 利用の流れ（導入〜継続のジャーニー）

1. <b>認知・想起のきっかけ</b>:
   - 請求額を見て後悔した瞬間や、SNSで他のユーザーの投稿・共有を見かけたとき。
2. <b>導入・初期設定</b>:
   - ユーザー登録（データ保護とセキュリティ担保）。
   - よく課金するゲームタイトルの事前登録（次回以降の入力コストを最小化）。
3. <b>利用・記録フロー</b>:
   - 課金直後、アプリを開いて「タイトル選択 → 金額ボタン選択 → 登録」の3タップ（約10秒）で完了。合計額は画面に出ないため気分を害さない。
4. <b>継続の動機</b>:
   - 「見たいときだけ」月ごとの課金履歴を確認し、自分の課金ペースを把握。
   - 「課金力」という表現により、罪悪感を薄めつつSNSでネタとして共有・交流する楽しさがある。

## 5. 既存サービス・競合調査

### 5-1. 競合サービスの分析

1. <b>かきんナビ（iOSアプリ）</b>
   - <b>特徴</b>: 棒グラフ・円グラフでの可視化、履歴やプリセットボタンによる入力補助。
   - <b>課題・違和感</b>:
     - ホーム画面に直接的な課金額が大きく表示されるため、使いすぎた月ほどアプリを開くのが億劫になる（ダチョウ効果）。
     - 「家計簿・節約」のトーンが強く、課金する楽しさを削いでしまう。
2. <b>Game Memo（iOSアプリ）</b>
   - <b>特徴</b>: ゲームタイトルからサムネイル検索が可能でビジュアルが綺麗。
   - <b>課題・違和感</b>:
     - リスト表示中心で過去との月別比較がしづらい。
     - ハードウェアや周辺機器など対象が広すぎて入力項目が多く、ガチャ課金の瞬発的な記録には重い。

### 5-2. それでも作りたい理由（不満・ズレの解消）

- 既存アプリは「正確に記録して支出を反省・我慢させる」設計になっており、ソシャゲユーザーの「ガチャを楽しみたい」というポジティブな感情と衝突しています。
- 必要なのは「反省させる監視アプリ」ではなく、<b>「記録する時は現実を突きつけず、振り返りたい時だけ自分のペースを教えてくれる」</b>重課金ユーザーの心理に寄り添った管理しすぎないアプリです。

### 5-3. 体験価値としての差別化

- <b>差別化の一文</b>:
  - <b>「課金管理が苦手で現実から目を背けがちな人が、罪悪感を感じず手軽に記録を続けられ、安心してガチャを楽しめる体験」</b>
- <b>具体的なアプローチ</b>:
  - <b>開いても金額が出ない安心感</b>: アプリ起動時や記録直後に合計額を表示せず、ユーザーが明示的に確認操作を行ったときのみ開示。
  - <b>「円」から「課金力」への言い換え</b>: 支出の生々しさをやわらげ、課金した記録を閲覧するハードルを下げるかつ、ゲームのステータス感覚やSNSのネタとして楽しめる世界観を提供。

### 6-1. ユーザーの変化

- <b>行動の変化</b>: 生活に支障をきたすような衝動的な課金が減り、計画的な課金ペースが身につく。

- <b>考え方の変化</b>: 課金を「罪悪感のある浪費」ではなく、「予算内で健全にゲームを楽しむためのエンタメ」として前向きに捉えられるようになる。

### 6-2. 価値の一文表現

## 7. このアプリで実現すること

### 7-1. MVPで実装する機能

- <b>ユーザー認証機能</b>
  - 新規登録・ログイン・ログアウト（課金データのセキュアな保存・端末間同期）
- <b>ゲームタイトル管理機能</b>
  - 課金対象タイトルの事前登録・一覧・編集・削除（次回以降の入力工数削減）
- <b>課金記録機能（3タップ入力）</b>
  - ゲームタイトル選択（ワンタップ）
  - 課金額選択（（よく課金する額面のプリセットボタン選択。※金額手入力や、プリセット額のカスタマイズ機能も想定）
  - 日付登録（デフォルトで当日日付を自動設定）
  - ※登録完了画面では合計金額を表示せず、記録のみを素早く完了
- <b>課金記録閲覧・振り返り機能</b>
  - 月別アーカイブ選択機能
  - 誤認防止のクッションUI（開いた直後は合計を非表示とし、ユーザーの明示操作で表示）
  - 月別課金記録一覧および全タイトルの課金合計額表示
  - 金額単位を「円」から「課金力」に変換表示

### 7-2. 本リリース（拡張）で実装する機能

- <b>SNS（X）共有機能</b>
  - 月間の「課金力」や記録実績を画像やテキストでX等にシェアできる機能。記録継続の動機づけとユーザー同士の交流を促進。
- <b>ゲームサムネイル画像設定機能</b>
  - タイトルごとに好みの画像をアップロード・設定できる機能。管理アプリの無機質なイメージを緩和し、愛着の湧くデザインにカスタマイズ可能にする。
- <b>操作音・SE演出</b>
  - ボタン選択時にソシャゲ風の効果音を再生し、操作する楽しさを向上。
- <b>月末のリマインダー通知</b>
  - 月末に通知を送り、課金記録の入力忘れを防止。

## 8. このアプリの懸念点とその対策

### 懸念点①：管理が苦手なユーザーは、記録自体を途中で投げ出してしまうのではないか

- <b>背景</b>: 自分自身も含め、管理が苦手な人は入力の手間が大きいとすぐに離脱してしまう。
- <b>対策</b>: タイトル事前登録 × プリセット金額ボタン × 当日自動入力により、アプリ起動から<b>3タップ・約10秒</b>で記録が完了する極小ステップを設計する。

### 懸念点②：課金額を見るのが怖くなり、アプリを開かなくなる（ダチョウ効果）

- <b>背景</b>: 実際の課金総額を突きつけられると罪悪感が生まれ、アプリ起動そのものを避ける心理が働く。
- <b>対策</b>:
  - アプリ起動画面や記録直後の画面には<b>合計額を一切表示しない</b>。
  - 閲覧ページでも2段階の明示操作を経て初めて表示される「クッションUI」を採用する。
  - 単位を「課金力」とし、視覚的・心理的な圧迫感を緩和する。

### 懸念点③：課金対象が広すぎて用途がわかりづらい

- <b>背景</b>: 最近のソシャゲでは、ガチャだけでなくサブスクリプション型の課金も増えています。これらも対象に含めると、どこまで管理すべきかがわかりにくくなります。
- <b>対策</b>: 対象を突発的かつ勢いで課金が膨らみやすい<b>「ソシャゲのガチャ課金」</b>に完全特化し、UIや訴求メッセージを一貫させる。サブスク型の課金は金額が一定で、1,000円を超えないものがほとんどのため、管理の必要性は低いと考えています。

### 9-1. 続けることで生まれる価値

- 課金データが蓄積されることで、自分の課金ペースや傾向（推しイベントの周期など）を客観的に把握できるようになる。

## 10. 技術スタック

### 10-1. 使用予定の技術

| 区分 | 選定技術 | バージョン / 補足 |
| --- | --- | --- |
| フロントエンド | React | SPA（Single Page Application）構成 |
| バックエンド | Ruby on Rails (APIモード) | 8.1系 |
| 開発言語 | Ruby | 3.3系 |
| データベース | PostgreSQL | 18系 |
| インフラ / デプロイ | Vercel（フロント） + Render（バック） | Web API連携構成 |
| スタイリング | Tailwind CSS | ユーティリティファーストCSS |
| 開発環境 | Docker / Docker Compose | コンテナ仮想化 |

### 10-2. 技術選定の理由

#### 前提

今回の主目的は、難しい技術や最新・最適な技術を選ぶことではなく、開発経験が少ない中でも、堅実かつ迅速に開発を進める経験を積むことです。また、講師やRUNTEQスクール生とのレビューを通じて、エンジニアとしてのコミュニケーション経験を積むことも重視しています。そのため、RUNTEQのカリキュラムで学習済みで、周囲にも相談しやすいReactとRuby on Railsを採用しました。

#### フロントエンド：React

- <b>比較検討</b>:
  - <i>Vue.js</i>: 学習コストが低く短期間での実装には有利ですが、市場での求人数や将来的な拡張性を考慮しReactを優先しました。
  - <i>Svelte / SolidJS</i>: 軽量かつ高パフォーマンスで魅力的ですが、日本語ドキュメントやトラブルシューティング情報が比較的少なく、初学者が単独開発する上で開発遅延のリスクが高いと判断し見送りました。

#### バックエンド：Ruby on Rails (APIモード)

- <b>比較検討</b>:
  - <i>Express / Laravel / FastAPI</i>: シェアや処理速度の観点で検討したものの、バックエンドの新規言語・フレームワーク習得に時間を費やすより、最も習熟しているRailsを用いてフロントエンド（React）や機能のブラッシュアップにリソースを集中させる判断をしました。

#### データベース：PostgreSQL

- <b>選定理由</b>: カリキュラムでの利用実績があり、デプロイ先であるRenderとの親和性が非常に高いため採用しました。

#### デプロイ先：Vercel（フロントエンド）＋ Render（バックエンド）

- <b>選定理由</b>: GitHubと連携したCI/CD環境が極めて容易に構築でき、低コストで安定した運用が可能なため。フロントエンドは高速なエッジ配信に優れたVercel、バックエンドはRails APIの運用実績が豊富なRenderを組み合わせる構成としました。初期の小規模開発においてインフラ構築のオーバーヘッドを避け、プロダクト開発の速度を最優先しています。

#### UIライブラリ / CSSフレームワーク：Tailwind CSS

- <b>選定理由</b>: 既存の学習経験があり、記法に慣れているためUI作成で手が止まるリスクを最小化できます。Reactのロジック実装やRailsとのAPI連携に開発リソースを集中させるため採用しました。（今後のUI洗練度向上に応じてshadcn/uiなどの導入も検討予定）

### 10-3. キャッチアップ不足による懸念事項

#### 開発上の懸念事項

- <b>スケジュールの見積もり</b>
  - 本リリースを見据え、現役エンジニアや学習同期からのコードレビューを積極的に受け入れ、チーム開発を見据えたコミュニケーション経験を積むことも重視しています。
  - そのためIssue作成やテストなど、経験の少ない作業に必要な時間・工数をまだ把握できていないため、スケジュールの見積もりが難しい状況です。
- <b>セキュリティ対策</b>
  - 課金履歴という個人データを扱うため、適切なセキュリティ対策が必要です。
  - セキュリティ要件や採用すべき技術について知見が不足しており、必要な対策の範囲を判断できていないことが懸念点です。
