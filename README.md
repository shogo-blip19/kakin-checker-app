# kakin-checker-app

ソシャゲのガチャ課金を手軽に記録・管理するWebアプリケーション

## 1. サービス概要

- **サービス名（仮）：** ガチャ課金チェッカー
- **概要**：  
  ソシャゲのガチャ課金を手軽に記録・管理するアプリです。  
  3タップで記録でき、合計額は見たいときだけ確認できます。  
  罪悪感や入力の負担を減らし、無理なく課金ペースを把握できます。
- **解決する課題**：
  - **対象**： ソシャゲのガチャに熱中して計画以上に課金してしまい、翌月の請求で後悔しがちな20〜30代のユーザー
  - **課題**： 課金をコントロールしたいが、従来の管理アプリは入力が面倒な上、アプリを開くたびに支出総額を突きつけられて現実逃避（ダチョウ効果）してしまい継続できない。記録を続けられないと課金管理がおろそかになり、後悔するほどの支出につながりやすくなります。
- **解決策：**
  - **極小ステップの入力導線：** タイトル選択から3タップ（約10秒）で完了する設計により、ゲーム熱中時の入力の手間を最小限にします。
  - **クッションUI（開閉設計）：** 記録直後やアプリ起動時に支出総額が目に入らない設計にし、「総額を見るのが嫌でアプリを開かなくなる（ダチョウ効果）」を物理的に防ぎます。
  - **「円」から「課金力」への単位変換：**
    - **定義：** 単純な等価変換とし、「1円 ＝ 1課金力」として表示します（例：月30,000円の課金 ＝ 30,000課金力）。
    - **心理的ハードルが下がる理由（なぜ等価でも圧迫感が減るのか）：**
      1. **現実の価値との比較遮断：** 「円」で表示されると、無意識に「このお金で服が買えた」「貯金できた」と現実の生活費と比較して強い後悔を生みます。独自単位に変換することでこの連想を断ち切り、後悔を和らげます。
      2. **実体験に基づく根拠（ポイントの心理効果）：** 過去に5年間、現金とポイント（1円＝1pt）の併用店舗でスタッフを経験した際、「現金だと渋るが、等価のポイントであれば躊躇なく使う」お客様を数多く見てきました。単位から「円」が外れるだけで、お金を失う心理的苦痛（メンタルアカウンティング）が劇的に下がることを現場で実感しており、この効果をUIに応用しています。
  - **目的意識に寄り添う「予算設定」と「クッション型アラート」：**
    - ユーザー自身の「これくらいに抑えたい」という前向きな意志を尊重し、心理的・操作的負担のない予算設定機能を搭載します。
    - 予算超過時もネガティブに責めるのではなく、視覚的に優しく状態を伝えることで、現実逃避を防ぎつつ自己調整を促します。

## 2. アイデアの背景

### 2-1. きっかけとなった体験・感情

- ソーシャルゲームで欲しいキャラクターをガチャで手に入れる瞬間は、日々の大きな楽しみでありストレス解消でもあります。
- 一方で、目当てのキャラが出ない興奮状態のまま勢いで課金を重ね、翌月の請求額を見て「想定以上に使ってしまった……」と強い罪悪感と後悔に苛まれる経験を何度もしました。
- その結果、せっかくキャラクターを入手できても、喜びより「いくら使ってしまったのか」という不安が勝ってしまい、ゲームを素直に楽しめなくなるジレンマに直面しました。

### 2-2. なぜそれが気になったのか

- 「来月は控えよう」と決意しても、ゲームに熱中すると同じ失敗を繰り返してしまい、根本的なペース管理ができていないことに気づきました。
- 課金を完全にゼロにして我慢したいわけではなく、「自分にとって安全な許容範囲を把握した上で、不安なく気持ちよくガチャを楽しみたい」という強い想いがあったためです。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

- 課金を管理したいと思っても、記録が億劫で三日坊主になり続かない。
- 家計簿アプリや決済明細では、日用品やサブスク等の他支出と混ざってしまい、純粋なソシャゲ課金額が把握しづらい。

### 3-2. 深掘りした真の課題（Whyの深掘り）

1. **なぜ管理が続かないのか？**
   - ガチャを回している興奮状態で、日付・タイトル・金額を細かく手入力するのが面倒だから。
   - 記録しようとするたびに「これまでの課金合計額」が目に飛び込んできて、楽しい気分が一気に冷めるから。
2. **なぜ金額を見ると気分が冷めるのか？**
   - 従来の管理アプリは「いくら使ったか」を直視させる設計のため、罪悪感からアプリを開くこと自体を避けてしまう（ダチョウ効果／ダチョウ症候群）。
3. **アプリを開かず、課金管理をやめてしまうとどうなってしまうのか？**
   - 支出のブレーキが効かなくなり、翌月の請求で青ざめるほどの行き過ぎた課金を繰り返してしまう。
   - その結果、苦労して手に入れたキャラクターを見るたびに罪悪感や請求額が頭をよぎり、ゲームを純粋に楽しめなくなってしまう。
4. **本当に解決したい課題**
   - 「入力のストレスと現実直視の苦痛を取り除いて記録を習慣化させ、ソシャゲへの行き過ぎた課金を防ぎ、安心してゲームを楽しめる状態を作ること」

## 4. 想定ユーザー

### 4-1. ターゲット像

- **年齢層**： 20〜30代（独身・社会人）
  - *選定根拠*： スマホゲームへの課金比率・可処分所得が最も高い年齢層であるため。
- **生活・状況**：
  - 可処分所得にある程度余裕があり、余暇はソシャゲやSNS（X等）に時間を費やす。
  - 期間限定ガチャや推しキャラが登場すると「出るまで引く」傾向があり、月末・翌月のクレカ請求を見て青ざめた経験がある。
- **利用環境と課題へのアプローチ**：
  - 課金を行う瞬間はゲームに熱中した興奮状態であり、すぐにゲームに戻りたいため、細かい入力フォームを埋めることは極めて困難。
  - **アプローチ**： 事前登録したタイトルから金額ボタンを選ぶだけの「3タップ／約10秒」で完了するUIを設計し、熱中状態を邪魔せず記録できる環境を実現します。

### 4-2. ユーザーとの距離感

- **当事者（自分自身）**
  - 自身の現在も続いているリアルな課金体験・後悔・管理挫折の経験から着想を得ており、ユーザーの細かな心理的機微（見たくない・でも把握したい）を当事者目線で正確に捉えています。

### 4-3. 需要と代替手段の比較

- **想定初期ユーザー**： SNS等で「課金しすぎてクレカが止まった」「今月の請求が怖い」と投稿しているソシャゲユーザー。
- **代替手段（現状）**： クレジットカード・決済アプリの利用明細、一般的な家計簿アプリ、メモ帳。
- **代替手段からの移行理由**：
  - クレカ明細は生活費等も含まれ、ソシャゲ単体の支出が直感的に見えにくい。
  - 家計簿アプリは「節約・我慢」を目的としており、課金を楽しむマインドと相反する。
  - 本アプリは「課金を否定せず、安心して楽しむための相棒」として機能するため、置き換えて利用する明確な価値があります。

### 4-4. 利用の流れ（導入〜継続のジャーニー）

1. **認知・想起のきっかけ**：
   - 請求額を見て後悔した瞬間や、SNSで他のユーザーの投稿・共有を見かけたとき。
2. **導入・初期設定**：
   - ユーザー登録（データ保護とセキュリティ担保）。
   - よく課金するゲームタイトルの事前登録（次回以降の入力コストを最小化）。
3. **利用・記録フロー**：
   - 課金直後、アプリを開いて「タイトル選択 → 金額ボタン選択 → 登録」の3タップ（約10秒）で完了。合計額は画面に出ないため気分を害さない。
4. **継続の動機**：
   - 「見たいときだけ」月ごとの課金履歴を確認し、自分の課金ペースを把握。
   - 「課金力」という表現により、罪悪感を薄めつつSNSでネタとして共有・交流する楽しさがある。

## 5. 既存サービス・競合調査

### 5-1. 競合サービスの分析

1. **かきんナビ（iOSアプリ）**
   - **特徴**： 棒グラフ・円グラフでの可視化、履歴やプリセットボタンによる入力補助。
   - **課題・違和感**：
     - ホーム画面に直接的な課金額が大きく表示されるため、使いすぎた月ほどアプリを開くのが億劫になる（ダチョウ効果）。
     - 「家計簿・節約」のトーンが強く、課金する楽しさを削いでしまう。
2. **Game Memo（iOSアプリ）**
   - **特徴**： ゲームタイトルからサムネイル検索が可能でビジュアルが綺麗。
   - **課題・違和感**：
     - リスト表示中心で過去との月別比較がしづらい。
     - ハードウェアや周辺機器など対象が広すぎて入力項目が多く、ガチャ課金の瞬発的な記録には重い。

### 5-2. それでも作りたい理由（不満・ズレの解消）

- 既存アプリは「正確に記録して支出を反省・我慢させる」設計になっており、ソシャゲユーザーの「ガチャを楽しみたい」というポジティブな感情と衝突しています。
- 必要なのは「反省させる監視アプリ」ではなく、**「記録する時は現実を突きつけず、振り返りたい時だけ自分のペースを教えてくれる」**重課金ユーザーの心理に寄り添った管理しすぎないアプリです。

### 5-3. 体験価値としての差別化

- **差別化の一文**：
  - **「課金管理が苦手で現実から目を背けがちな人が、罪悪感を感じず手軽に記録を続けられ、安心してガチャを楽しめる体験」**
- **具体的なアプローチ**：
  - **開いても金額が出ない安心感**： アプリ起動時や記録直後に合計額を表示せず、ユーザーが明示的に確認操作を行ったときのみ開示。
  - **「円」から「課金力」への言い換え**： 支出の生々しさをやわらげ、課金した記録を閲覧するハードルを下げるかつ、ゲームのステータス感覚やSNSのネタとして楽しめる世界観を提供。

### 6-1. ユーザーの変化

- **行動の変化**： 生活に支障をきたすような衝動的な課金が減り、計画的な課金ペースが身につく。

- **考え方の変化**： 課金を「罪悪感のある浪費」ではなく、「予算内で健全にゲームを楽しむためのエンタメ」として前向きに捉えられるようになる。

> 「このサービスは、課金の管理が苦手なソシャゲユーザーが、罪悪感なく手軽にペースを把握し、安心してガチャを楽しめるようになるサービスです。」

## 7. このアプリで実現すること

### 7-1. MVPで実装する機能

**■ ユーザー認証機能**

1. **ユーザー新規登録機能**
2. **ログイン機能**
3. **ログアウト機能**

**■ ゲームタイトル管理機能**

4. **ゲームタイトル登録機能**（課金対象タイトルの事前登録）
5. **ゲームタイトル一覧表示機能**
6. **ゲームタイトル編集機能**
7. **ゲームタイトル削除機能**

**■ 課金記録・振り返り機能**

8. **課金記録の作成機能**
   - 【仕様】タイトル選択（ワンタップ）、金額入力（固定プリセット＋手入力）、当日の日付自動設定を組み合わせ、最短3タップ（約10秒）で記録を完了させる。記録完了直後は合計額を表示しない。
9. **課金アーカイブ選択機能（クッションUI）**
   - 【仕様】振り返り画面にアクセスした際、個別の金額や合計額は一切目に入れさせず、記録が存在する「○年○月」などの期間選択のみを表示する。
10. **課金履歴の一覧表示機能**
    - 【仕様】ユーザーが明示的に期間を選択したタイミングで初めて、その期間に登録された個別の課金履歴データを一覧で表示する。
11. **合計金額の「課金力」変換・表示機能**
    - 【仕様】履歴一覧の表示に合わせて、対象期間の合計課金額を算出し、「円」ではなく後悔を和らげる「課金力（1円=1課金力）」の単位で表示する。
12. **課金記録の編集機能**（誤入力時の金額・タイトルの修正）
13. **課金記録の削除機能**（誤入力時の取り消し）

**■ 予算管理機能**

14. **目標予算設定・保存機能**
    - 【仕様】「今月の目標課金力（例：30,000課金力）」をワンタップまたは手入力で設定可能（初期登録時・後からでも設定可）。
15. **予算・進捗の表示・警告（クッション型アラート）機能**
    - 【仕様】予算超過時は過度な圧迫感を与えないマイルドな視覚変化（色変更等）で状態を課金登録画面で伝える。
16. **目標予算の編集機能**
17. **目標予算の削除（リセット）機能**

### 7-2. 本リリース（拡張）で実装する機能

- **SNS（X）共有機能**
  - 月間の「課金力」や記録実績を画像やテキストでX等にシェアできる機能。記録継続の動機づけとユーザー同士の交流を促進。
- **ゲームサムネイル画像設定機能**
  - タイトルごとに好みの画像をアップロード・設定できる機能。管理アプリの無機質なイメージを緩和し、愛着の湧くデザインにカスタマイズ可能にする。
- **操作音・SE演出**
  - ボタン選択時にソシャゲ風の効果音を再生し、操作する楽しさを向上。
- **月末のリマインダー通知**
  - 月末に通知を送り、課金記録の入力忘れを防止。

## 8. このアプリの懸念点とその対策

### 懸念点①：管理が苦手なユーザーは、記録自体を途中で投げ出してしまうのではないか

- **背景**： 自分自身も含め、管理が苦手な人は入力の手間が大きいとすぐに離脱してしまう。
- **対策**： タイトル事前登録 × プリセット金額ボタン × 当日自動入力により、アプリ起動から**3タップ・約10秒**で記録が完了する極小ステップを設計する。

### 懸念点②：課金額を見るのが怖くなり、アプリを開かなくなる（ダチョウ効果）

- **背景**： 実際の課金総額を突きつけられると罪悪感が生まれ、アプリ起動そのものを避ける心理が働く。
- **対策**：
  - アプリ起動画面や記録直後の画面には**合計額を一切表示しない**。
  - 閲覧ページでも2段階の明示操作を経て初めて表示される「クッションUI」を採用する。
  - 単位を「課金力」とし、視覚的・心理的な圧迫感を緩和する。

### 懸念点③：課金対象が広すぎて用途がわかりづらい

- **背景**： 最近のソシャゲでは、ガチャだけでなくサブスクリプション型の課金も増えています。これらも対象に含めると、どこまで管理すべきかがわかりにくくなります。
- **対策**： 対象を突発的かつ勢いで課金が膨らみやすい**「ソシャゲのガチャ課金」**に完全特化し、UIや訴求メッセージを一貫させる。サブスク型の課金は金額が一定で、1,000円を超えないものがほとんどのため、管理の必要性は低いと考えています。

## 9. 今後の展開・発展の方向性

### 9-1. 続けることで生まれる価値

- 課金データが蓄積されることで、自分の課金ペースや傾向（推しイベントの周期など）を客観的に把握できるようになる。
- 単なる「支出の記録」にとどまらず、自分が熱中したゲームの歩み・思い出ログとしての価値を持つ。

### 9-2. ユーザー同士の繋がり

- 「今月の課金力」をSNSで共有することで、ソシャゲプレイヤー同士の共感やネタとしての交流を生み出す。

### 9-3. UI・UXのゲーミング化

- 管理ツール特有の堅苦しさを排除し、ダークモードやゲーム調の配色、効果音演出を取り入れ、起動すること自体が楽しいプロダクトを目指す。

### 10-2. 技術選定の理由

#### 前提

今回の主目的は、難しい技術や最新・最適な技術を選ぶことではなく、開発経験が少ない中でも「堅実かつ迅速に開発を進め、最後まで作り切る経験」を積むことです。また、講師やRUNTEQスクール生とのレビューを通じて、エンジニアとしてのコミュニケーション経験を積むことも重視しています。

#### 【MVPリリース時の技術選定】

- **フレームワーク：Ruby on Rails（フルスタック）**
  - **選定理由：** 最も学習時間が長く、慣れ親しんでいる技術であるためです。当初はReactを用いたSPA構成を検討していましたが、初期から複数技術を組み合わせると実装難易度が上がり、完成しないリスクがあるというレビューを受け、方針を転換しました。フレームワークをRails一つに絞ることで、実装速度を最大化し、スケジュールの見通しを確実に立ててMVPをリリースすることを最優先としています。また実装速度を意識しながらも、今後のReactへの移行も見据えて、どのようにコードを書くと移行しやすいかを確認しながら進めていきます。
- **データベース：PostgreSQL**
  - **選定理由：** カリキュラムでの利用実績があり、デプロイ先であるRenderとの親和性が非常に高いため採用しました。
- **インフラ / デプロイ：Render**
  - **選定理由：** MVP段階ではRails単体での構成となるため、Vercelは使用せずRenderにデプロイを統一します。初期のインフラ構築の学習コストを抑え、プロダクト開発にリソースを集中させます。
- **UIライブラリ：Tailwind CSS**
  - **選定理由：** 既存の学習経験があり、記法に慣れているためUI作成で手が止まるリスクを最小化できます。（今後のUI洗練度向上に応じてshadcn/uiなどの導入も検討予定）

#### 【MVPリリース以降の技術移行予定】

- **フロントエンド：React / バックエンド：Rails (APIモード) への移行**
  - **移行理由：** MVP完成後は、アプリの動作をさらに効率化し、画面遷移の速度を向上させるために、Reactを用いたSPA構成へアップデートする予定です。「3タップ入力」などの主要機能において、ユーザーがストレスなくシームレスに操作できるUXを提供することを目指します。
  - **インフラ変更：** SPA化に伴い、フロントエンドのデプロイ先として高速なエッジ配信に優れたVercelを導入し、Vercel(React) + Render(Rails API)の構成へ移行します。

### 10-3. キャッチアップ不足による懸念事項

#### 開発上の懸念事項

- **スケジュールの見積もり**
  - 本リリースを見据え、現役エンジニアや学習同期からのコードレビューを積極的に受け入れ、チーム開発を見据えたコミュニケーション経験を積むことも重視しています。
  - そのためIssue作成やテストなど、経験の少ない作業に必要な時間・工数をまだ把握できていないため、スケジュールの見積もりが難しい状況です。
- **セキュリティ対策と認証方式について**
  - 課金額というプライベートな情報を扱うため、安全な認証とアクセス制御（他人のデータが閲覧できない設計）の実装が必須です。
  - **MVPにおける認証方式の検討：** MVPはRailsのフルスタック構成となるため、まずは確実な実装を優先し、学習経験のある標準的なセッションベースの認証（SorceryなどのGem）を用いて安全な基盤を構築します。
  - **将来のSPA化を見据えた学習課題：** MVPリリース後、フロントエンドをReactに置き換える際には、トークンベースのAPI認証（`devise_token_auth` など）へ認証方式を移行する必要があります。そのため、初期設計時から将来の切り替えを頭の片隅に置きつつ、SPA化に向けたセキュリティ要件（トークンの安全な保持など）のキャッチアップを並行して進めることが今後の課題です。
